## 修复 started 误报（内核无 inbound 仍报 started）

- 根因：`buildInbound` 返回 nil（协议不被内核支持，如 xray×hysteria v1）时，`buildConfig` 仅打 warn 照常生成空 inbound 配置，`Start` 成功，服务层 `startKernel` 打 `started, N users`——节点实际不监听。
- 修复：两内核拒绝无 inbound 配置启动。xray 在 `marshalConfig`（`internal/kernel/xray/xray.go:649`）检查 `cfgMap["inbounds"]` 为空即返回 error；singbox 在 `SingBox.Start`（`internal/kernel/singbox/singbox.go:96`）同判。`buildConfig` 的 warn 块删除（由 error 取代，避免双重告警）。
- 服务层效果：`startKernel` 走既有 error 路径打 `failed to start kernel`，不再误报 started；老实例不受影响（Start Phase 1 失败早于实例创建）。
- 测试：`TestMarshalConfig_RejectsMissingInbound`（xray，hy1 反例 + vmess 正例）、`TestStart_RejectsMissingInbound`（singbox，unknown-proto 反例 + box 必须为 nil）。`go test -race -count=1 ./internal/...` 全绿。
- E2E 复验（docker compose，重建镜像）：node15/xray 日志 `ERROR failed to start kernel error=protocol "hysteria" produced no inbound (unsupported by kernel)`；node26/singbox 正常 `started, 1 users` + curl 204。
- 已知取舍：内核起不来的节点每个同步周期会重试并打一条 error（诚实可见，替代原静默假 started）。

## kernel.type=auto + SS2022-chacha20 调查与校验

- **auto 模式**：`kernel.type: auto` 按节点 spec 解析内核，一个实例跑满全部协议。解析规则（`model.ResolveKernelForNode`）优先级：面板 `kernel_type` 显式指定 > singbox-only 协议（tuic/anytls/naive/socks/http/mieru/hysteria v1）> transport 强制（xhttp/splithttp→xray，h2/http/quic→singbox，复用既有表）> vmess+Reality→xray（singbox 会静默降明文）> 默认 singbox。显式 kernel.type 行为不变（仅 transport 不匹配时翻转，即原 machine 模式语义）。
- service 层惰性建内核：auto 时 `newService` 放 singbox 占位，`initialSetup`/`handleWSEvent`/`applyPullResult` 拿到 spec 后 `resolveAutoKernel`→`ensureKernelFor` 按需构建；热更新换协议触发换内核（旧内核 Stop+重建，主循环串行无竞态，kernelMu 保护）。日志 `kernel auto-selected` 可审计。
- machine 模式预取改用 `ResolveKernelForNode`（含 protocol/Reality 规则，transport 规则是其子集）。
- **SS2022-chacha20 多用户不做**（协议硬限制，查证 SIP022 规范 + Xray `inbound_multi.go` `only aes methods are supported` + sing-box 文档：EIH 只在 AES 变体 separate header 里，chacha 变体无此构造；单用户 chacha 理论可行但 Xboard 多用户语义下无意义）。落地：`ValidateNodeSpec` 对 `2022-blake3-chacha*` 配置期报清晰错误，替代内核深层 `invalid argument`。
- 测试：`TestResolveKernelForNode_Auto`（21 用例表驱动）、`TestResolveKernelForNode_ExplicitKernel`、`TestValidateNodeSpec_SS2022ChachaRejected`。`make test` 全绿。

## 晚：SS2022-chacha20 multi-user 显式拒启（builder 层兜底）

- 根因定论：sing-shadowsocks 服务端 iPSK（`users[]` 形态）只实现 blake3-aes，chacha20 multi-user 本身不存在（SIP022 多用户 EIH 仅 AES 变体）；叠加面板对 chacha20 不下发 server_key（空 server password）。此前 `invalid argument` 即此双因。
- 修复：双内核 `buildShadowsocks`（xray `config.go:319`、singbox `config.go:498`）检测 chacha20-poly1305 → 专项 error log（指明 aes-only + 替代 cipher）+ 返回 nil → 既有 no-inbound 拒启接管（xray `marshalConfig` / singbox `SingBox.Start`）。
